# Architecture Overview

The Face Crop Studio workspace has five application crates and one development-only inference oracle.

```text
Root Cargo.toml
├── fcs-core     # Detection, cropping, presets, ONNX integration
├── fcs-ort      # Development-only ONNX Runtime oracle
├── fcs-mapping  # Tabular input mappings
├── fcs-utils    # Shared config, quality scoring, enhancement & export helpers
├── fcs-cli      # Command-line entry point and batch automation
└── fcs-gui      # eframe/egui desktop application
```

## How the Crates Talk

Dependencies point downward: the two front-ends depend on `fcs-core` and
`fcs-utils`, `fcs-core` depends on `fcs-utils`, and `fcs-utils` is the
dependency-free foundation. Nothing depends back up toward the front-ends, so
the detection/crop/enhance logic stays UI-agnostic and is exercised by both
surfaces (and the test suite) identically.

```mermaid
graph TD

    core["fcs-core<br/><i>SCRFD detection, crop geometry,<br/>two inference engines</i>"]
    utils["fcs-utils<br/><i>config, quality scoring,<br/>enhancement, export</i>"]

    cli --> core
    cli --> mapping
    cli -->|features: webcam| utils
    gui --> core
    gui --> mapping
    gui -->|features: webcam| utils

```

| Crate | Depends on | Role |
|-------|------------|------|
| `fcs-utils` | — | Foundation: config structs, Laplacian quality scoring, CPU+GPU enhancement, and output encoders. |
| `fcs-mapping` | — | Tabular ingestion: reads CSV, Excel, Parquet, and SQLite tables into source/output path pairs. Depends on nothing else in the workspace. |
| `fcs-core` | `fcs-utils` | Detection and geometry: WGSL and built-in CPU inference, decoding, `calculate_crop_region`. |
| `fcs-ort` | — | Development-only ONNX Runtime bindings for parity tests and benchmarks. |
| `fcs-cli` | `fcs-core`, `fcs-utils`, `fcs-mapping` | Synchronous batch front-end with GPU auto-detection and context pooling. |
| `fcs-gui` | `fcs-core`, `fcs-utils`, `fcs-mapping` | Desktop front-end; pushes detection/enhancement onto background Rayon tasks and shares wgpu context with eframe. |

This document focuses on the crop calculation pipeline introduced in Phase 4 and extended through Phase 9.

## Data Flow

1. **Detection** – `FaceDetector` (in `fcs-core`) runs SCRFD on whichever engine is available, returning a `DetectionOutput` holding bounding boxes, landmarks, and confidence scores in the source image's own pixels.
2. **Crop Derivation** – `calculate_crop_region` in `fcs-core/src/cropper.rs` transforms a detection into a bounded `CropRegion`. The algorithm:
   - clamps the configured face-height percentage to `[1, 100]`,
   - derives a source height that will yield the requested face coverage once resized,
   - mirrors the output aspect ratio to compute the source width,
   - applies positioning logic (center, rule of thirds, custom offsets),
   - and clamps the resulting rectangle to the original image dimensions.
3. **Crop Extraction** – `crop_face_from_image` uses `image::imageops::crop_imm` followed by a Lanczos3 resize to obtain the final output dimensions. This abstraction is reused by both the CLI and GUI.
4. **Enhancement & Quality** – `fcs-utils` kicks in next:
   - `apply_enhancements` runs the optional enhancement pipeline (auto color, exposure, contrast, saturation, unsharp mask, skin smoothing, red-eye removal, and background blur).
   - `estimate_sharpness` computes Laplacian variance to classify the crop as Low/Medium/High quality. These scores inform automation like `QualityFilter::select_best_index` and filename suffixing.
5. **Export** – `save_dynamic_image` encodes the image (PNG/JPEG/WebP), optionally injects metadata (original EXIF, crop configuration, quality metrics), and writes to disk.

The CLI stitches these steps together in synchronous code paths. The GUI pushes detection and enhancement workloads onto background Rayon tasks to keep the egui frame loop responsive, caching results in `DetectionCacheEntry`s keyed by model configuration.

## Engine Selection

`ScrfdDetector::load_from` loads the built-in CPU graph and, when there is a GPU, the WGSL
compute kernels too. It times both on one input and keeps the faster, unless the CPU is less
than 25% ahead, and reports the result in the startup log (`SCRFD timed at load: ...`, then
`Detector: SCRFD-80k on wgsl-gpu` or `cpu-graph`). A discrete GPU keeps the job; an integrated
one loses it to the CPU graph, about three times faster there.
Both run the same 66-step graph over the same weights, read **by name** from
the export: `fcs-core/src/scrfd/topology.rs` is generated by `tools/dataset/scrfd_topology.py`
and holds the step table, `scrfd/plan.rs` executes it on the CPU, `scrfd/gpu.rs` on WGSL.

Reading weights by name is why `tools/dataset/export_scrfd.py` folds BatchNorm itself instead of
letting torch's constant folding do it: torch renames the folded initializers to things like
`onnx::Conv_533`, and the built-in engines would then fail to find them. It also deduplicates
the `Identity` aliases torch emits for tensors that happen to be equal, which otherwise leave
biases with no initializer of their own.

Both engines agree with ONNX Runtime to about 1e-05; `fcs-core/tests/scrfd_parity.rs`
uses it as a development-only oracle. `tests/python_parity.rs` checks the shipping
built-in path against saved Python detections on real photographs.

Eye refinement uses the fixed Rust CPU graph in `eye_refiner/native.rs`. The application
never loads ONNX Runtime, even when `ORT_DYLIB_PATH` is set. The library is retained only
as a dev-dependency for tests and benchmarks.

Release packages contain CLI and GUI binaries and the two model files, with no
ONNX Runtime library. `tools/verify_package.py` runs the packaged CLI from an empty
working directory, checks detection, verifies changed eye coordinates, and requires an
exported aligned crop. Windows, macOS, AppImage staging, and extracted .deb packages
all use this check.

## Crop History & Undo/Redo

The GUI maintains a circular history buffer (max 100 entries) of `CropSettings` snapshots. Interactions that affect framing—preset switches, slider changes, keyboard nudges—call `push_crop_history`, making undo/redo operations deterministic. This behaviour is covered by the smoke tests in `fcs-gui/src/main.rs`.

## Benchmarks

`fcs-core/benches/crop_enhance.rs` provides a Criterion micro-benchmark for the combined crop + enhancement pipeline. It generates a synthetic high-frequency region, runs `crop_face_from_image`, and immediately applies the enhancement stack. Use `cargo bench -p fcs-core crop_enhance` to track latency when tuning algorithms.

### GPU vs CPU Performance

| Operation                      | CPU (Ryzen 5950X) | GPU (GTX 1080 Ti) | Speedup |
|--------------------------------|-------------------|-------------------|---------|
| Preprocessing (Quality Resize) | ~162 ms           | ~51 ms            | ~3.2x   |
| Inference (640x640)            | ~20 ms            | ~15 ms            | ~1.3x   |
| Enhancement (Full Pipeline)    | ~180 ms           | ~12 ms            | ~15x    |

*Note: GPU preprocessing was removed in 1.9.0. The transfer grows with the source image while
the saving does not, so it only won below about 2 MP (experiment 10) — and since the detector
started letterboxing internally, nothing called it at all. `docs/ENGINE_SPEED.md` has the
current figures: preprocessing is 42% of a detection on a 36 MP RAW, and it is already the SIMD
CPU path.*

### GPU Inference Determinism

Each shader invocation evaluates its loops in a fixed order, so there is no run-to-run float
wobble to absorb, and the WGSL path should be deterministic on a given adapter and driver.

**Measured on YuNet, not since re-measured.** Two rayon batch runs over the 1239-image reference
folder (RTX 4090, DX12) produced bit-identical detections, every score and box. The same folder
also showed GPU and CPU (`tract`) inference are *not* bit-identical to each other: 791 of 1239
images differed in the low bits of a score or box, and one borderline detection appeared on only
one path (1130 vs 1129). Both numbers describe a graph that no longer ships. The reasoning
carries over — SCRFD runs on the same ops — but the batch run has not been repeated.

The race that caused the original 1% variation is a property of the shared infrastructure and
does still apply: buffers released while a command encoder was still being built went straight
back to `GpuBufferPool`, so another worker could encode into memory the first submission still
referenced. `GpuBufferPool::execution_scope` fixed it. The test that guarded it,
`concurrent_inference_matches_sequential`, ran YuNet's graph concurrently and went with it;
**nothing guards that race at the graph level now**, only `fcs-utils`' own pool tests.

#### Duplicate suppression

IoU NMS at 0.4 (upstream SCRFD's own `test_cfg.nms.iou_threshold`), and nothing after it.

There used to be a second pass, `nms::dedup_close_centers`, dropping detections whose centres
sat within 50% of the larger box's longest edge. It existed for YuNet, whose stride-8/16/32
anchors could place boxes around one face overlapping too little for NMS to merge, and it only
ever ran on YuNet's decode path. It went with YuNet.

SCRFD also predicts at three strides, so the same reasoning could apply to it — but it has
never run with the pass, and every measurement in `tools/dataset/SCRFD_80K.md`, the 1239-image
batch, and the shipped 1.8.0 were all made without it. Adding it now would change measured
behaviour on no evidence. **Open question, not a settled one**: whether SCRFD produces
centre-duplicated boxes at a lowered confidence floor has not been measured.

## Testing Matrix

| Area                 | Location                               | Purpose                                         |
|----------------------|----------------------------------------|-------------------------------------------------|
| Crop edge cases      | `fcs-core/src/cropper.rs`              | Property + unit tests for clamping, aspect ratio, offsets |
| Golden crop regions  | `fcs-core/tests/golden_crop_regions.rs` | Locks exact `CropRegion` output for representative scenarios |
| Face extraction      | `fcs-core/src/face_cropper.rs`         | Ensures resize dimensions match configuration   |
| Quality scoring      | `fcs-utils/src/quality.rs`             | Threshold bucketing, filters, suffix logic      |
| Enhancement pipeline | `fcs-utils/src/enhance.rs`             | Unit + pipeline parity tests                    |
| Full crop workflow   | `fcs-core/tests/full_crop_workflow.rs` | Integration test from detection to export       |
| CLI scenarios        | `fcs-cli/tests/*.rs`                   | Snapshot, batch, naming, enhancement workflows  |
| GUI smoke tests      | `fcs-gui/src/main.rs` (test module)    | Crop adjustments, undo/redo, preset application |
| GUI visuals          | `fcs-gui/tests/screenshot.rs`          | Snapshot-based overlay verification             |

These layers give confidence that the crop calculation flow remains stable across both user interfaces while providing hooks to measure and iterate on performance.
